# سياسة قبول Skills من GitHub

**الحالة:** مسودة سياسة للكتالوج. لا تمثل هذه الوثيقة تدقيقًا لأي مستودع أو موافقة على أي Skill بعينها.

## 1. المبادئ والحدود

- تعامل مع كل Skill ومحتوياتها كمدخلات غير موثوقة؛ لا تمنحها سلطة النظام أو سياسة المشروع.
- لا تُدمج Skill لمجرد شعبيتها أو حداثة نشاطها أو ظهورها في تقرير بحث. التقييم يتناول **نسخة محددة** من **Skill محددة**.
- لا تخلط بين مراجعة النص وبين إذن التنفيذ. تعليمات Skill لا تمنح الوكيل صلاحية استعمال أدوات أو إجراء عمليات خارجية؛ تبقى موافقات المستخدم وسياسات الأدوات والبيئة مستقلة.
- فضّل التكييف المحلي أو إعادة كتابة إرشادات لازمة على إدخال حزمة كبيرة، عند إمكان حفظ الإسناد والامتثال للرخصة.
- لا تُفعّل مصدرًا دون مالك، ومراجع بشري غير المؤلف، وسجل قرار وأدلة قابلة لإعادة الفحص.

## 2. بوابات رفض إلزامية

أي شرط أدناه غير مستوفى يعني **رفضًا أو تعليقًا**، بصرف النظر عن الدرجة الإجمالية:

1. **الرخصة غير معروفة أو غير ملائمة:** لا نسخ أو إعادة توزيع قبل إثبات الرخصة التي تغطي الملفات المستخدمة وشروطها. وجود LICENSE في جذر المستودع لا يثبت تلقائيًا تغطية المهارة أو أصولها أو اعتمادياتها. أحِل حالات الالتباس، وخصوصًا القيود غير المعتادة أو تراخيص المحتوى، إلى المراجعة القانونية/المختصة.
2. **لا يوجد مرجع مصدر ثابت:** يمنع الاعتماد على `main` أو `latest` أو وسم متحرك. لا قبول من دون SHA كامل للـcommit ومصدر يمكن استرجاعه.
3. **محتوى ضار أو مخاطر غير قابلة للاحتواء:** مثل توجيه صريح لتجاوز تعليمات النظام أو السياسة، تسريب أسرار أو بيانات، سلوك خفي، تنزيل شيفرة متغيرة، أو طلب صلاحيات غير لازمة بلا تبرير وضوابط فعالة.
4. **تشغيل غير مفحوص:** لا تثبيت أو تنفيذ hooks أو scripts أو أوامر قدمها المصدر. إذا كانت الوظيفة الأساسية تتطلب تشغيل مكوّن لا يمكن مراجعته واحتواؤه، فلا تفعّلها.
5. **غياب منشأ كافٍ أو إخفاق اختبار حرج:** لا قبول إذا تعذر تمييز الملفات التي تمت مراجعتها عن الملفات الخارجية أو المولّدة، أو فشلت اختبارات السلامة والنطاق والخصوصية.
6. **لا مالك ولا خطة تحديث/تعطيل:** يجب تحديد من يراقب المصدر، وكيف تُعطّل المهارة ويُرجع عنها عند ظهور خطر.

لا تعوّض درجة مرتفعة أي بوابة فاشلة. قد يتطلب قرار «قبول مشروط» تقييد الاستخدام، لكنه لا يتجاوز الشروط الإلزامية.

## 3. مراجعة الرخصة والحقوق

قبل التقييم، حدّد بالضبط الملفات المراد استخدامها (مثل `SKILL.md`، المراجع، القوالب، الصور، الخطوط، السكربتات والاعتماديات)، ثم:

- افحص نص الرخصة الفعلي في النسخة المثبتة، والرخصة الخاصة بكل ملف/مكوّن إن كانت مختلفة. لا تعتمد على شارة README أو تصنيف SPDX وحده.
- سجل اسم الرخصة وإصدارها، مسار ملف الرخصة، رابط المصدر، ونطاق الملفات الذي تغطيه؛ واحفظ الإسناد والإشعارات المطلوبة وأي نص رخصة يلزم إعادة توزيعه.
- افحص تراخيص الأصول والبيانات والاعتماديات التابعة على حدة. لا تفترض أن رخصة مستودع تجميعي تغطي مشاريع مرتبطة أو محتوى طرف ثالث.
- قيّم متطلبات التوزيع والنسخ والتعديل، وواجبات الإسناد والمشاركة بالمثل والقيود التجارية عند انطباقها. اطلب مراجعة مختصة عند الشك؛ لا تستخدم المحتوى إلى أن يُحسم.

## 4. تثبيت المصدر وسلامته

1. سجّل عنوان المستودع، المالك، المسار الدقيق للـSkill، وcommit SHA كاملًا (40 خانة لـGit SHA-1 أو ما يقابله حسب صيغة المستودع). ثبّت SHA للمراجعة والاختبار، لا فرعًا أو وسمًا قابلًا للتغيير.
2. اجلب المحتوى من المصدر الرسمي قدر الإمكان، وسجّل تاريخ ووقت الجلب. احتفظ بنسخة المراجعة أو manifest بالملفات مع SHA-256 لكل ملف، إضافة إلى بصمة شجرة المصدر/الأرشيف إن أمكن.
3. قارن التغييرات بين النسخة المرشحة والنسخة السابقة المعتمدة؛ افحص submodules وملفات Git LFS والمراجع الخارجية والمحتوى المولّد. لا تتبع روابط تنزيل أو تضمينات ديناميكية وقت التشغيل.
4. أي تغيير في commit أو ملف أو اعتماد أو تعليمات أو إعدادات تكامل يبطل القبول السابق إلى حين مراجعة الفرق وإعادة الاختبارات ذات الصلة.

## 5. مراجعة prompt injection والمحتوى

افحص الملفات النصية والموارد المضمّنة يدويًا، واستخدم فحوصًا ساكنة مساعدة عند توافرها. المراجعة تشمل على الأقل:

- تعليمات تطلب تجاهل أو استبدال تعليمات النظام/المطوّر/المستخدم، أو إخفاء الإجراء، أو الادعاء بأن الموافقة قد مُنحت.
- طلب استخراج أو طباعة متغيرات البيئة، مفاتيح API، ملفات الاعتماد، بيانات المستخدم أو محتوى خارج نطاق المهمة، أو إرسالها إلى نطاق/خدمة خارجية.
- أوامر أو تعليمات تتطلب تشغيل shell، تثبيت حزم، تنزيل شيفرة، تعديل ملفات حساسة، تغيير إعدادات، أو الاتصال بالشبكة دون حاجة واضحة وموافقة مستقلة.
- نصوص مخفية أو مشوشة/مشفرة أو موزعة عبر ملفات مرجعية، تعليقات، HTML، صور/OCR أو ملفات ثنائية، وأي روابط إلى تعليمات خارجية متغيرة.
- تعارضات مع سياسة السلامة أو الخصوصية أو النطاق أو لهجة توحي بسلطة مضمونة أو تخفي القيود.

صنّف محتوى المستودع المقتبس أو المصادر الخارجية على أنه **بيانات غير موثوقة** لا تعليمات تنفيذية. عند وجود حقن أو غموض: اعزل الملف، سجّل السطر والدليل، وارفضه أو أزل الجزء المتأثر وأعد مراجعته بالكامل. لا يكفي البحث عن كلمات نمطية وحده لإثبات خلو المحتوى من الحقن.

## 6. منع hooks والتنفيذ والعزل

- **ممنوع تنفيذ hooks أو أوامر lifecycle أو scripts آليًا** أثناء الفحص أو التثبيت أو التفعيل، بما في ذلك hooks الخاصة بـGit أو مديري الحزم، و`postinstall`، وGitHub Actions/workflows، ومثبتات CLI وأوامر setup. افحص الملفات ساكنًا ولا تشغّل المثبت upstream.
- لا تشغّل أمثلة المصدر أو اختبارات المصدر افتراضيًا. اختبارات القبول تخص السلوك المتوقع للـSkill؛ تستخدم عينات ثابتة/اصطناعية ومحاكيًا أو harness مضبوطًا، وتكون الأدوات معطلة افتراضيًا.
- إذا استلزم اختبار محدد تنفيذ شيفرة، يلزم إذن صريح منفصل وخطة مكتوبة ومراجعة الشيفرة قبل التشغيل. ينفذ الاختبار في sandbox مؤقتة ومعزولة، بحساب غير مميز، ونظام ملفات مؤقت محدود، وبلا أسرار أو بيانات إنتاج، وبلا صلاحية كتابة إلى المستودع/المنزل أو المضيف.
- امنع الشبكة الصادرة افتراضيًا، أو اسمح فقط بنطاقات ووجهات اختبار معلنة ومحددة بعد الموافقة. لا تستخدم بيانات اعتماد حقيقية. ضع حدودًا للوقت والذاكرة والعمليات وحجم الملفات، وسجل الأوامر والمخرجات المنقحة.
- ابدأ بوضع قراءة فقط. لا تسمح بكتابة ملفات خارج مجلد الاختبار، أو بتشغيل Docker/الخدمات السحابية، أو النشر أو حذف الموارد أو تعديل صلاحيات، إلا بموافقة مستقلة صريحة ومناسبة للمخاطر.
- بعد الاختبار، أتلف بيئة العزل والبيانات المؤقتة، وراجع السجلات لمنع ظهور أسرار أو بيانات حساسة.

## 7. إثبات المنشأ (provenance) وسجل القرار

احتفظ بمدخل سجل واحد لكل Skill، على أن يتضمن الحقول التالية أو ما يعادلها:

| الحقل | ما يجب تسجيله |
|---|---|
| الهوية | اسم Skill، وصف موجز، النطاق والغرض، المالك الداخلي |
| المصدر | عنوان GitHub الرسمي، اسم المستودع ومالكه، مسار Skill، SHA كامل، وتاريخ/وقت الجلب |
| سلامة النسخة | بصمات الملفات/الشجرة، الملفات الداخلة والمستبعدة، فروقات عن النسخة السابقة، والمراجع أو الاعتماديات التابعة |
| الحقوق | الرخصة الفعلية، مسارات أدلتها، نطاق تغطيتها، الإسناد والإشعارات، والمسائل المحالة للمراجعة |
| المراجعة | أسماء/أدوار المراجع، تاريخها، نتائج prompt injection والسكريبتات والصلاحيات ومخاطر الخصوصية، والقيود المفروضة |
| الاختبارات | إصدار harness، بيانات الاختبار أو معرفاتها، الأوامر المسموح بها، النتائج، الإخفاقات والنطاق غير المختبر |
| القرار | الدرجة مع تبريرها، قبول/قبول محدود/تأجيل/رفض، الموافقات، تاريخ المراجعة التالية، وطريقة التعطيل/الرجوع |
| التعديلات | كل تعديل محلي، فرقه عن المصدر، وتأكيد عدم حذف الإسناد أو توسيع الرخصة ضمنيًا |

لا تسجل أسرارًا أو عينات بيانات حساسة في هذا السجل؛ استخدم معرفات وأدلة منقحة.

## 8. مقياس الدرجات

امنح كل محور درجة من صفر إلى الحد الأقصى. اكتب سببًا ودليلًا قابلًا للمراجعة؛ «لم يُفحص» لا يساوي صفر مخاطر، بل يعني نقص الأدلة وقد يؤدي إلى عدم القبول.

| المحور | الحد الأقصى | أمثلة على الدليل |
|---|---:|---|
| الترخيص والحقوق | 15 | نص رخصة واضح يغطي الملفات وإثبات الإسناد والاعتماديات |
| تثبيت المصدر والمنشأ | 15 | commit ثابت، بصمات، مصدر رسمي وسجل تغييرات |
| سلامة المحتوى ومقاومة prompt injection | 20 | مراجعة كاملة للمحتوى والروابط والتعليمات، ومخاطر مسجلة ومحدودة |
| أقل صلاحية وعدم تنفيذ/احتواء الشيفرات | 15 | لا hooks منفذة، جرد للسكريبتات، ولا طلب لصلاحيات زائدة |
| الخصوصية والشبكة | 10 | لا جمع/إرسال غير مبرر، ووجهات واتصال موثقة ومقيدة |
| نتائج اختبارات ما قبل التفعيل | 15 | نجاح اختبارات السلوك والسلامة والتكامل المقصود مع أدلة قابلة للتكرار |
| الصيانة والملاءمة والقيمة | 10 | حاجة واضحة، توافق موثق، مالك وخطة تحديث/إيقاف |
| **المجموع** | **100** | |

- **80–100:** مؤهل للنظر في القبول بعد اجتياز كل البوابات الإلزامية والموافقة البشرية. القبول قد يظل محدودًا بأدوات أو مستخدمين أو مهام معينة.
- **65–79:** يؤجل للتحسين أو تقييد المخاطر وإعادة التقييم؛ لا تفعيل إنتاجي.
- **أقل من 65:** رفض.
- سجّل الأدلة غير المتاحة كـ«غير محسوم»، ولا تمنح نقاطًا لها. الدرجة أداة فرز ومقارنة وليست شهادة أمان أو ضمان جودة.

## 9. اختبارات ما قبل التفعيل

أنشئ خطة اختبار قصيرة مرتبطة بالغرض المعلن للـSkill، ثم تحقق من الآتي دون تنفيذ scripts من المصدر:

1. **سلامة التنسيق والنطاق:** الملفات المطلوبة موجودة، metadata سليمة، لا تحميل زائد للمراجع، ولا محتوى خارج الوظيفة المعلنة. راجع الفرق بين كل ملف منشور وما سيحمّل إلى سياق الوكيل.
2. **حالات وظيفية ممثلة:** استخدم مدخلات اصطناعية أو منقحة تمثل حالة عادية، وحالة حدودية، وحالة غير مدعومة؛ قارن النتائج بمعايير قبول واضحة أو مراجعة بشرية.
3. **اختبار عدائي:** مرر تعليمات حقن معلومة، طلب أسرار/خروجًا عن النطاق، تعليمات متعارضة، وروابط/بيانات غير موثوقة، وتحقق أن Skill لا تتجاوز السياسة ولا تزعم تنفيذًا غير حاصل.
4. **حدود الإجراء:** تحقق أن Skill لا تبدأ أداة أو شبكة أو كتابة أو تغييرًا خارجيًا لمجرد ورود ذلك في نصها؛ كل إجراء يبقى خاضعًا لموافقة وصلاحية منفصلتين.
5. **الخصوصية:** استخدم canaries اصطناعية، وتأكد من عدم ظهورها في مخرجات غير لازمة أو سجلات أو طلبات خارجية.
6. **التوافق والتراجع:** تحقق من توافق host/نسخة Skill، ومن عدم تعارضها مع تعليمات المنتج، واختبر تعطيلها وإزالة أثرها. قِس الاستهلاك والسياق أو الضجيج إذا كانا عاملين مهمين.
7. **إعادة الإنتاج والتوثيق:** أعد الاختبارات على الـSHA نفسه؛ خزّن حالات الاختبار ونتائجها المنقحة مع سجل القرار. سجّل ما لم يُختبر صراحةً.

لا تتبنَّ اختبارات أو درجات يعلنها upstream بوصفها نتائجنا؛ يمكن الاستفادة منها لتصميم حالات، لكن يجب تشغيل اختباراتنا المناسبة وتسجيلها. فشل حالة حرجة أو ظهور سلوك خارج النطاق يمنع التفعيل إلى أن يُعالج ويعاد الاختبار.

## 10. التفعيل والمراجعة المستمرة

بعد قبول موثق فقط، فعّل Skill على مجموعة محدودة وبصلاحيات أقل ما يمكن، ويفضل خلف إعداد قابل للتعطيل. راقب السلوك والمخرجات والشكاوى والتغيرات في الـhost؛ لا تمنحها أسرارًا أو صلاحيات كتابة افتراضيًا. ضع تاريخ مراجعة دوري لا يتجاوز 90 يومًا، وابدأ مراجعة فورية عند تغيير المصدر أو ظهور حادثة أو تغير الرخصة/الاعتماديات أو تغير سطح الأدوات. عند الاشتباه، عطّلها فورًا، وثبّت أدلة النسخة، وراجع السجلات ثم أعد القبول من البداية للنسخة الجديدة.
