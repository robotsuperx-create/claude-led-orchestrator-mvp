# دليل مهارات ووكلاء المنتج والهندسة

## أفضل خمسة خيارات مفتوحة المصدر

اختيرت القائمة وفق مدى تغطية تحليل المتطلبات ومواصفات المنتج والقرارات المعمارية والتوثيق والتخطيط، مع فحص README والرخصة ونشاط المستودع. مؤشرات النشاط أدناه لقطة من GitHub بتاريخ **5 أكتوبر 2026**؛ عدد النجوم أو حداثة الدفع لا يثبتان جودة المخرجات. الأفضل دمج الأدوات بحسب دورها، لا تثبيت الحزم كلها معاً.

### 1. PM-Skills — أقوى مكتبة متخصصة في أعمال المنتج

[المستودع](https://github.com/product-on-purpose/pm-skills) مناسب لمرحلة اكتشاف المشكلة والتحقق منها إلى إعداد PRD وتسليم قصص المستخدم. يغطي البحث التركيبي للمقابلات، التحليل التنافسي، صياغة المشكلة والفرضيات، ترتيب الأولويات، ومهارات ADR وتبرير التصميم، ثم قصص المستخدم ومعايير القبول. ويوفر 68 مهارة، وستة وكلاء فرعيين، وسير عمل، وأمثلة للمخرجات؛ كما يتبع مواصفة Agent Skills ويمكن تثبيته عبر أكثر من أداة. لذلك هو أفضل نقطة بدء لمهام البحث المنتجّي وتحويل نتائجه إلى مواصفات قابلة للتسليم. [1]

**الرخصة والنشاط:** Apache-2.0، والمستودع غير مؤرشف؛ أظهر GitHub آخر دفع في 4 أكتوبر 2026. [2]

**مخاطر الاعتماد:** المكتبة ليست بديلاً عن مقابلات المستخدمين أو مصادر السوق الأصلية؛ على الفريق إرفاق الأدلة ومراجعة الاستنتاجات. كثرة المهارات قد تشجع على مخرجات شكلية أو استخدام غير متناسق إن لم تُختَر منها مجموعة صغيرة. وثمة تنبيه مهم: خادم MCP المصاحب في وضع الصيانة، لذا يوصي README بالتثبيت كإضافة/مهارات بدلاً من بناء الاعتماد الجديد على MCP. [1]

### 2. GitHub Spec Kit — الأقوى لتثبيت المتطلبات وربطها بالخطة

[المستودع](https://github.com/github/spec-kit) يحوّل الفكرة إلى مواصفات، ثم خطة تقنية ومهام قابلة للتنفيذ، ويتابع التنفيذ حتى التحقق من التقارب مع المواصفة. يتضمن كذلك مساراً مستقلاً لتقييم الأفكار يجمع البحث والتعريف والتشكيل وينتهي بقرار موثق مثل «امضِ» أو «استوضح» أو «أوقف». هذه البنية تجعله مرشحاً قوياً عندما تكون الأولوية لتقليل الغموض وربط قرار المنتج بخطة التنفيذ بدلاً من بدء البرمجة مباشرة. [3]

**الرخصة والنشاط:** MIT، غير مؤرشف؛ سجل GitHub آخر دفع في 3 أكتوبر 2026. [4]

**مخاطر الاعتماد:** سير العمل والقوالب يضيفان خطوات وملفات، وقد يكونان أثقل من اللازم لتغيير صغير. مخرجات المواصفة والخطة تظل مسودات مولدة تحتاج مراجعة مالك المنتج والمهندس، لا عقداً صحيحاً تلقائياً. كما أن جودة القرار البحثي تعتمد على تزويد الوكيل بأدلة موثوقة؛ وجود مرحلة اسمها «بحث» لا يضمن وحده بحثاً خارجياً أو تحققاً مستقلاً. [3]

### 3. BMAD Method — إطار متكامل بأدوار منتج ومعمارية

[المستودع](https://github.com/bmad-code-org/BMAD-METHOD) يقدم منهج تطوير مرناً يمتد من توضيح التغيير وتخطيطه إلى البناء والتحقق والتعلم. يمكن استدعاء وجهات نظر متخصصة في المنتج والعمارة وتجربة المستخدم والتطوير والاختبار، مع نقل موجزات المنتج والمواصفات والقرارات إلى خطوات التنفيذ. يناسب المشروعات الكبيرة أو الفرق التي تريد طريقة عمل موحدة تشمل التحليل والتخطيط والتنفيذ بدلاً من حزمة مهارة منفردة. [5]

**الرخصة والنشاط:** ملف LICENSE نصه MIT، لكن واجهة GitHub API لم تتعرف على SPDX وأرجعت `NOASSERTION`؛ ينبغي التحقق من الملف نفسه عند تثبيت نسخة محددة. المستودع نشط وغير مؤرشف، وآخر دفع مسجل في 4 أكتوبر 2026. اسم BMad وعلاماته التجارية لا يمنح الترخيص حق استخدامها كعلامة للمنتج. [6] [7]

**مخاطر الاعتماد:** إطار واسع ومتعدد الوكلاء قد يرفع استهلاك السياق والزمن، ويخلق وثائق متكررة إن جُمِع بلا تمييز مع Spec Kit أو PM-Skills. يلزم اختيار المسار المناسب لحجم التغيير ومراجعة نقاط التسليم بين الأدوار، لا اتباع كل مرحلة آلياً. راجع أيضاً إشعار العلامة التجارية في LICENSE/TRADEMARK قبل إعادة تسمية أو توزيع منتج مشتق. [5] [6]

### 4. wshobson/agents — أفضل كتالوج متعدد الأدوات لأدوار التقنية والتوثيق

[المستودع](https://github.com/wshobson/agents) يجمع مهارات ووكلاء وأوامر موزعة على إضافات، ويدعم عدة بيئات مثل Claude Code وCodex وCursor وOpenCode وGitHub Copilot. تبرز قيمته في الأدوار التقنية الدقيقة: `backend-architect` لتصميم REST API وحدود الخدمات ومخططات البيانات، و`api-documenter` لمواصفات OpenAPI/Swagger ووثائق المطورين، و`docs-architect` للتوثيق التقني، إضافة إلى مراجعي المعمارية ومولد المراجع والدروس. الدليل يسرد 202 وكيلاً محلياً؛ كما يوثق README فحوص البنية والتوليد والتوثيق. [8] [9]

**الرخصة والنشاط:** MIT، غير مؤرشف؛ آخر دفع مسجل في 4 أكتوبر 2026. [10]

**مخاطر الاعتماد:** هو كتالوج كبير لا منهج واحد متماسك لتحليل المنتج. اختر الإضافات والأدوار المطلوبة فقط، وافحص اختلاف إمكانات كل بيئة تشغيل؛ صيغ الوكلاء والصلاحيات والنماذج قد تتغير عبر المحولات. يصرّح المشروع أن تقييماته القائمة على أحكام نموذجية ومحاكاة مونت كارلو تجريبية وغير متحققة مقابل أحكام بشرية، لذا لا تعتبر درجاتها دليلاً على صحة النتائج. كما أن أي إضافة خارجية لها رخصتها ومتطلبات تثبيتها الخاصة، ولا تفترض أن ترخيص المستودع يغطيها. [8]

### 5. Superpowers — الأفضل لمرحلة بلورة الفكرة وخطة عمل هندسية منضبطة

[المستودع](https://github.com/obra/superpowers) يقدم منهج تطوير مبنياً على مهارات قابلة للتركيب. يبدأ بمهارة `brainstorming` لصقل الفكرة ومناقشة البدائل وإقرار التصميم، ثم `writing-plans` لتقسيم العمل إلى مهام صغيرة مع مسارات الملفات وخطوات التحقق، ويواصل التنفيذ عبر وكلاء فرعيين أو خطة تنفيذ متتابعة. يدعم ذلك تطويراً منظماً ومراجعة التصميم قبل الكود؛ وهو مكمل مناسب لحزمة تعالج المحتوى المنتجّي نفسه، لا بديل عن مكتبة PM أو توثيق API متخصصة. [11]

**الرخصة والنشاط:** MIT، غير مؤرشف؛ آخر دفع مسجل في 27 سبتمبر 2026. [12]

**مخاطر الاعتماد:** يفرض سير عمل قد يبطئ التغييرات العاجلة أو البسيطة، وقد يتداخل مع منهج التخطيط الموجود في BMAD أو Spec Kit. احتفظ بمُنسّق واحد للمراحل حتى لا تطلب الأدوات تصميمين وخطتين متنافستين. يصف README إشارة قياس اختيارية مرتبطة بميزة المصاحب المرئي، ويذكر أنها لا تشمل تفاصيل المشروع ويمكن تعطيلها عبر متغير البيئة `SUPERPOWERS_DISABLE_TELEMETRY`؛ راجع الإعدادات وسياسة المؤسسة قبل اعتمادها. [11]

## المكدس المرشح

**مكدس خفيف وعملي لمعظم فرق المنتجات البرمجية:**

1. **PM-Skills** للاكتشاف، تجميع أبحاث المستخدمين، صياغة المشكلة، إعداد PRD، قصص المستخدم ومعايير القبول، وقرارات ADR الأولية.
2. **Spec Kit** لتثبيت متطلبات الميزة المقبولة في مواصفة، تحويلها إلى خطة ومهام، والتحقق من التنفيذ مقابل المقصود.
3. **wshobson/agents** مع تفعيل انتقائي لدوري `api-documenter` و`docs-architect` و`backend-architect` عند الحاجة إلى مراجع API أو مراجعة قرار تقني.

أضف **Superpowers** بدلاً من خطوات العصف الذهني والتخطيط العامة في Spec Kit إذا كان الفريق يريد مهام تنفيذ دقيقة ومراجعات متكررة، أو استخدم **BMAD Method** بديلاً عن تنسيق Spec Kit عندما تحتاج العملية إلى أدوار واضحة للمنتج والعمارة وتجربة المستخدم في دورة واحدة. لا أوصي بتشغيل BMAD وSpec Kit وSuperpowers جميعاً كمنسقين أساسيين في المشروع نفسه؛ التداخل يضاعف المستندات ويصعّب معرفة أي مخرجات هي المرجع.

ضع بوابات بشرية واضحة: اعتماد صاحب المنتج على PRD ومعايير القبول، واعتماد مهندس مسؤول على ADR ومخطط API، والتحقق الآلي من OpenAPI والروابط والاختبارات حيث أمكن. اعتبر المحتوى المقترح من أي وكيل مسودة؛ اربطه بمصادره، وراجع مخاطر الخصوصية والشفرة أو التعليمات المضمنة في المستودعات والوثائق قبل إدخالها إلى سياق الوكيل.
