# Claude-led multimodel MVP: architecture and integration plan

## الحالة والنطاق

تم تجميع نتائج الوكلاء في حزمة TypeScript مستقلة داخل `packages/claude-led-orchestrator`. هذه الحزمة **MVP تجريبي غير موصول بتطبيق Agent Orchestrator**: لم تتغير خدمات Go أو daemon أو عقود HTTP/OpenAPI أو واجهة Electron/React أو قاعدة البيانات. الهدف هو تثبيت العقود وحدود المسؤولية واختبارها قبل أي توصيل تشغيلي.

تُصدّر واجهة الحزمة العامة من `src/index.ts`. يظل `ModelRouter` مسؤولاً عن اختيار محوّل/نموذج، بينما يمثل `ModelGateway` في المنسّق واجهة التخطيط والمراجعة؛ وهما حدّان مختلفان يجري حقنهما من المستدعي ولا يقدّمان تنفيذاً شبكياً.

## ما بُني

- **عقود المهمة (`task-contract.ts`):** أنواع ومعالجات تحقق runtime لعقد المهمة، معايير القبول، أوامر التحقق، سياسة التصعيد، ملخص التغييرات ونتيجة الوكيل.
- **Model Gateway (`model-gateway.ts`):** موجّه يختار محوّلاً محقوناً من claude وdeepseek وkimi وgemini وopenai، وفق نوع المهمة وقدرات النموذج ومستوى التكلفة. لا توجد SDKs أو مفاتيح أو اتصالات شبكية؛ يجب على المستدعي توفير المحوّلات.
- **إدارة السياق (`context-manager.ts`):** تجميع حتمي لملخصات وفروق ملفات مسموح بها فقط ضمن ميزانية تقريبية للرموز. لا يقرأ الملفات بنفسه ولا يرسلها إلى مزود.
- **ضبط التكلفة (`cost-controller.ts`):** تجميع الاستخدام والتكلفة التي يبلّغها المستدعي، وفحص حدود إجمالي الرموز/الإنفاق وقرار إعادة المحاولة. لا يتضمن أسعاراً ولا يفرض حدّ الإنفاق على نقل فعلي.
- **سياسة الأمان (`security-policy.ts`):** قرار صلاحيات قراءة/كتابة المسارات وقائمة سماح/منع أوامر. هذه فحوص تطبيقية ساكنة وليست sandbox؛ لا تنفذ I/O ولا تحل الروابط الرمزية ولا تمنع تجاوزها من المستدعي.
- **المنسّق التنفيذي (`executive-orchestrator.ts`):** دورة التخطيط عبر Claude، التفويض إلى العمال المحددين بالخطة، جمع النتائج وإعادة المحاولة، التحقق، مراجعة Claude، ثم قرار `merge` أو `hold`. كل التخزين والتنفيذ والنماذج واجهات محقونة؛ التنفيذ الحالي تسلسلي ولا ينشئ عمليات أو تغييرات ملفات بنفسه.
- **الاختبارات:** اختبارات وحدات من `node:test` مع doubles محلية؛ لا تحتاج إلى مزود أو إنترنت.

## البناء والتحقق دون اتصال

لا توجد تبعيات runtime أو حزم npm مطلوبة. في بيئة Node.js 22.13 أو أحدث، شغّل من جذر الحزمة:

```bash
npm test
npm run typecheck
npm run build
# أو جميعها بالتتابع
npm run check
```

الاختبارات تستخدم دعم Node التجريبي لإزالة أنواع TypeScript (`--experimental-strip-types`). البناء والتحقق النوعي يستخدمان `tsc` المتاح محلياً على `PATH`؛ لا تستدعِ هذه الأوامر الشبكة ولا تثبّت التبعيات. ينتج البناء ملفات ESM وتعريفات TypeScript تحت `dist/`، وهي نواتج مولّدة وليست مصدراً للتعديل اليدوي.

## حدود التكامل الحالية

1. لا توجد محوّلات مزود فعلية، أو إدارة أسرار، أو timeout/cancellation، أو بث، أو retries على مستوى النقل، أو قياس موثوق لفواتير المزود.
2. تقدير الرموز في مدير السياق heuristic (أربعة محارف UTF-16 تقريباً لكل رمز)، وليس tokenizer لمزود أو ضماناً لحدوده.
3. سياسة المسارات والأوامر لا تحقق وصول الملفات أو تشغيل العمليات؛ هي ليست عزلاً، ولا تتعامل مع symlink/TOCTOU، أو الشبكة، أو الموارد، أو البيئة والـPATH.
4. لا يوجد تخزين دائم، استئناف تشغيل، idempotency، سجلات تدقيق، أو حواجز موافقة. حالة orchestration مؤقتة في الذاكرة.
5. أسماء Claude/المزودين تصف نقاط التوجيه فقط؛ لا تعني أن هذه الحزمة تستبدل مسارات Claude ACP/CLI أو محادثات Chat المستمرة في المنتج.

## خطة الربط اللاحقة

### 1. daemon وbackend

- حسم سياسة البيانات الخارجة، موافقة المستخدم، حدود الإنفاق، الإلغاء والمهلات قبل تفعيل أي إرسال إلى مزود.
- إضافة port ضيق مستقل في `backend/internal/ports` ومحوّل backend حقيقي في `backend/internal/adapters`، ثم خدمة تطبيقية خلف إعداد/feature flag وتوصيلها من daemon. لا تخلط Model Gateway مع `ports.ChatDriver` أو `reviewgateway`؛ مسارات Chat الحالية تملك تاريخ المحادثة والاستئناف والموافقات وfencing.
- ربط `WorkerRuntime` و`ProjectMemory` و`Validator` بواجهات backend القائمة فقط. يجب التحقق من السياسة عند نقطة الوصول الفعلية؛ تمرير الأوامر المقبولة كـargv مع `shell: false`، واستخدام جذر عمل موثوق ووسائل عزل فعلية.
- إبقاء قرار الدمج منفصلاً عن دمج git أو تعديل workspace؛ يتطلب تطبيق قرار الدمج فحوص backend وموافقة/صلاحيات مناسبة. أضف سجلات/استئناف ومهاجرات SQLite فقط بعد تحديد الحاجة، مع idempotency وCDC وفق قواعد المستودع.

### 2. API والواجهة

- بعد استقرار خدمة daemon، أضف controller وDTO ومصدر OpenAPI في المسارات المعتمدة، ثم أعد توليد الأنواع (`npm run api`) بدلاً من تحرير الأنواع المولّدة يدوياً.
- أضف hooks ومكوّنات React لعرض حالة التشغيل والميزانية والنتيجة وقرار `hold`، ولإجراءات المستخدم والموافقات. تبقى الاعتمادات ومفاتيح المزود داخل daemon فقط؛ لا تمررها للrenderer أو السجلات أو قاعدة البيانات كنص صريح.
- لا تضف منفذاً جديداً أو تعرض المسار عبر LAN افتراضياً؛ راجع مصادقة/سياسات الشبكة والاختبارات ذات الصلة قبل إطلاق أي endpoint.

### 3. بوابة الإطلاق

ابدأ بمحوّل واحد تجريبي، اختبارات fake provider وتكامل محلي، حدود تكلفة وإلغاء قابلة للملاحظة، وfeature flag مع تعطيل فوري. نفّذ اختبارات عقود وخدمات وAPI/واجهة وsmoke قبل توسيع المزودين. راجع كذلك `01-repo-audit.md` و`05-security-notes.md` للتدقيق ومخاطر التنفيذ.
