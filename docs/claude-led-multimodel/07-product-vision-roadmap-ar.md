# رؤية مشروع Claude-Led Multimodel Orchestrator

## 1. الفكرة في جملة واحدة

المشروع هو **طبقة قيادة وتنسيق آمنة فوق Agent Orchestrator**: يفهم Claude الهدف الكبير، يحوله إلى مهام صغيرة قابلة للتنفيذ، يوزعها على عمال برمجيين ونماذج مختلفة، يعزل كل عامل داخل Worktree وDocker Sandbox، يتحقق من النتائج، ثم يقدم للمستخدم توصية واضحة: **دمج، تعديلات مطلوبة، أو إيقاف للمراجعة البشرية**.

المشروع لا يحاول استبدال Agent Orchestrator أو Claude Code أو Codex أو بقية الوكلاء؛ بل يجعلها تعمل كنظام واحد قابل للمراقبة بدل مجموعة جلسات منفصلة.

---

## 2. المشكلة التي يحلها المشروع

عند استخدام وكيل واحد، تكون المهمة بسيطة نسبيًا. لكن عندما يصبح المشروع أكبر وتعمل عدة وكلاء بالتوازي تظهر مشاكل واضحة:

- من يقرر ما الذي يجب تنفيذه أولًا؟
- كيف نقسم الهدف الكبير إلى مهام مستقلة؟
- كيف نمنع عاملين من تعديل الملفات نفسها؟
- كيف نعرف أي عامل مسؤول عن كل تغيير؟
- كيف نتحقق من أن مخرجات العامل صحيحة وليست مجرد رسالة نجاح؟
- كيف نمنع وكيلًا من الوصول إلى أسرار الجهاز أو الشبكة أو مجلدات خارج المشروع؟
- كيف نعيد المحاولة بعد فشل اختبار أو مراجعة؟
- كيف يعرف المستخدم ما يحتاج إلى تدخله الآن؟
- كيف نحتفظ بتاريخ القرارات والسياق دون كشف الأسرار لمزود خارجي؟

الحل هو تحويل العمل من **محادثات مستقلة** إلى **دورة تشغيل هندسية قابلة للتتبع**.

## 3. تجربة المستخدم المستهدفة

### المسار الأساسي

1. يفتح المستخدم مشروعًا أو مستودعًا.
2. يكتب هدفًا كبيرًا، مثل:
   > أضف نظام مصادقة آمنًا مع اختبارات وتوثيق ودعم الاستعادة.
3. يقرأ Claude المشروع والسياق المسموح به.
4. يولد خطة تتضمن:
   - ملخص الهدف.
   - المهام الفرعية.
   - الاعتماديات بين المهام.
   - الملفات أو المناطق المحتملة للتعديل.
   - معايير القبول.
   - اختبارات التحقق.
   - مستوى المخاطر.
5. يراجع المستخدم الخطة ويوافق عليها أو يعدلها.
6. ينشئ النظام Workers لكل مهمة.
7. يحصل كل Worker على:
   - Worktree أو مساحة معزولة.
   - تعليمات محددة.
   - سياق محدود وملائم.
   - نموذج أو Agent مناسب.
   - أوامر مسموح بها فقط.
8. يعمل العمال داخل Docker Sandbox عند تفعيل العزل.
9. يشغّل Validator اختبارات ثابتة ومحددة.
10. يجمع Claude النتائج ويراجعها.
11. تظهر النتيجة في Kanban:
   - Working.
   - Needs you.
   - In review.
   - Ready to merge.
12. يقرر المستخدم الدمج أو يطلب تعديلات أو يعيد تشغيل المهمة.

### مبدأ مهم

المنسق لا يقرر الدمج بصمت، ولا ينفذ `git merge` تلقائيًا في النسخة الآمنة الأولى. دوره هو تقديم **توصية قابلة للتفسير**، بينما يبقى القرار النهائي والعملية الحساسة تحت تحكم المستخدم وسياسات المشروع.

## 4. المكونات الرئيسية

## 4.1 Executive Orchestrator

العقل المنظم للمشروع:

- فهم الهدف.
- قراءة سياق المشروع المسموح.
- إنشاء خطة تنفيذ.
- تحديد المهام المستقلة.
- تحديد الاعتماديات.
- اختيار Worker وModel لكل مهمة.
- متابعة التقدم.
- إعادة المحاولة عند الفشل.
- إرسال نتائج التحقق إلى المراجع التنفيذي.
- إصدار توصية `merge` أو `hold`.
- تسجيل القرارات المهمة.

يجب أن يبقى هذا المكون منسقًا لا منفذًا مباشرًا للملفات. التنفيذ الحقيقي يمر عبر Ports وخدمات محددة.

## 4.2 Model Gateway

واجهة موحدة لاستدعاءات النماذج، دون خلطها مع Chat المستمر:

- Claude للتخطيط والقرارات والمراجعة التنفيذية.
- DeepSeek أو نموذج اقتصادي للمهام البرمجية المتكررة.
- Kimi أو Gemini أو OpenAI كخيارات إضافية لاحقًا.
- اختيار النموذج حسب:
  - نوع المهمة.
  - مستوى الصعوبة.
  - سرعة الاستجابة.
  - التكلفة.
  - السياق المطلوب.
  - القدرات المعلنة.
- مهلات وإلغاء.
- إعادة محاولة محدودة.
- Redaction قبل الإرسال.
- حد أقصى للتوكنز والتكلفة.
- تسجيل Usage دون حفظ الأسرار.
- منع النموذج من تغيير مزود أو نموذج خارج السياسة.

الـGateway ليس بديلًا عن Chat Driver أو ACP؛ فالمحادثات طويلة العمر والاستئناف والموافقات تظل تحت خدمات Chat الحالية.

## 4.3 Worker Runtime

وحدة تنفيذ مهمة واحدة:

- تستقبل مهمة ثابتة من الخطة.
- تتحقق من وجود Worktree صحيح.
- تشغل أوامرًا من Allowlist.
- لا تضيف نص المهمة إلى `argv`.
- لا تستخدم Shell عند تشغيل الأوامر.
- تشغل عدة محاولات بحد أقصى محدد.
- تعيد نتيجة typed:
  - completed.
  - failed.
  - blocked.
- تحفظ ملخصًا ومخرجات محدودة.
- تربط النتيجة بالمهمة والفرع والـWorktree والـPR.

## 4.4 Validator

طبقة تحقق مستقلة عن كلام العامل:

- تشغيل اختبارات الوحدة.
- فحص النوع والبناء.
- Lint.
- فحص Git diff.
- فحص ملفات مطلوبة.
- فحص معايير القبول.
- تشغيل كل أمر كـargv ثابت.
- تحديد حدود الإخراج.
- إخفاء الأسرار من stdout وstderr.
- اعتبار رمز خروج غير صفري فشلًا.
- عدم اعتبار رسالة العامل دليل نجاح.
- تشغيل Validator داخل نفس Docker Sandbox عند تفعيل العزل.
- رفض غياب Worktree أو اختلاف Worktrees بطريقة fail-closed.

## 4.5 Worktree Manager

إدارة مساحة كل عامل:

- إنشاء Worktree أو ربط Worktree قائم.
- فرع مستقل لكل مهمة.
- منع تصادم الفروع والمسارات.
- ربط المسار بالـWorker والـRun.
- تنظيف آمن بعد الإغلاق.
- عدم حذف Worktree يعمل فيه Process.
- التعامل مع Windows file locking.
- فحص حالة Git قبل وبعد التنفيذ.
- كشف التعديلات غير المتوقعة.

## 4.6 Docker Sandbox

حد التنفيذ الحقيقي للعمال وValidator:

- `--network none`.
- Filesystem للـimage read-only.
- Mount لمشروع واحد فقط إلى `/workspace`.
- Workdir داخل `/workspace`.
- `cap-drop=ALL`.
- `no-new-privileges`.
- حد ذاكرة.
- حد CPU.
- حد PIDs.
- `/tmp` مؤقت ومحدود.
- Image allowlist.
- عدم استخدام `--privileged`.
- عدم تمرير Docker socket إلى الحاوية.
- عدم تمرير Environment كامل للمضيف.
- عدم تمرير مفاتيح API إلى Worker إلا عند وجود Broker صريح ومحدود.
- Timeout وإلغاء حقيقيان.
- تسجيل سبب الإيقاف والحدود التي تم تطبيقها.

العزل ليس مجرد `BuildDockerCommand`؛ يجب أن يكون التنفيذ الفعلي عبر Runtime يفرض القيود.

## 4.7 Project Memory

ذاكرة المشروع ليست سجلًا كاملًا لكل ملف أو كل Prompt. هدفها حفظ:

- هدف المشروع.
- القرارات المعمارية.
- القيود التي اختارها المستخدم.
- معايير القبول.
- ملخصات النتائج.
- أسباب الرفض أو التعديل.
- ملخصات فشل سابقة.
- تفضيلات المشروع.

يجب أن تكون الذاكرة:

- محدودة الحجم.
- قابلة للحذف.
- قابلة للتصدير.
- منفصلة عن الأسرار.
- قابلة للتدقيق.
- قابلة لتعطيل الإرسال الخارجي.

## 4.8 Review and Merge Gate

بوابة مستقلة قبل الدمج:

- فحص حالة CI.
- فحص مراجعات GitHub.
- فحص التعارضات.
- فحص الملفات المعدلة.
- فحص نتيجة Validator.
- فحص موافقة المستخدم عند الحاجة.
- إظهار أسباب `hold` بوضوح.
- عدم تنفيذ Merge عند وجود فشل مخفي.
- Idempotency عند إعادة محاولة العملية.

## 6. الأمان: ما يجب أن يكون غير قابل للتفاوض

### تهديدات يجب منعها

- Prompt injection من README أو Issue أو ملف داخل المشروع.
- تسريب API keys وSSH keys وTokens.
- وصول العامل إلى Home Directory.
- Mount غير مقصود للـDocker socket.
- الاتصال بالشبكة رغم تعطيله.
- Shell injection عبر task أو metadata.
- استخدام `../` أو symlink للخروج من Worktree.
- TOCTOU بين فحص المسار والتنفيذ.
- تمرير Environment المضيف كاملًا.
- تنفيذ Image غير موثوقة.
- Container escape.
- استهلاك CPU أو RAM أو PIDs بلا حدود.
- تسريب stdout/stderr إلى UI أو Model.
- تنفيذ Merge تلقائي بعد نتيجة مزيفة.
- Replay أو تكرار Run يسبب تغييرات إضافية.
- صلاحيات LAN زائدة.
- تعارض Workerين على نفس Worktree.

### القاعدة الأمنية الأساسية

> السياسة التطبيقية وحدها ليست Sandbox.

قائمة الأوامر المسموحة مفيدة، لكنها لا تعوض:

- حاوية حقيقية.
- Mount مضبوط.
- Network policy.
- Resource limits.
- Environment isolation.
- Symlink وTOCTOU checks.
- Broker للصلاحيات الحساسة.
- Audit trail.

### مفاتيح API

في النسخة الآمنة:

- تبقى المفاتيح داخل daemon أو secret manager.
- لا تدخل renderer.
- لا تدخل Worker's environment افتراضيًا.
- لا تُحفظ في SQLite كنص صريح.
- لا تظهر في Logs أو Errors.
- لا يرسلها Worker إلى الإنترنت لأن الشبكة معطلة.
- إذا احتجنا Provider access من الحاوية، نستخدم Broker ضيقًا يسمح بطلبات محددة فقط مع حدود وتدقيق.

## 7. الحالة الحالية المعروفة

ما تم إنجازه في فرع `main` حتى الآن:

- عقود Orchestrator وخدمات التخطيط والتنفيذ والمراجعة.
- Worker Runtime مع أوامر ثابتة.
- Docker Sandbox اختياري للعامل.
- صورة `ao/worker:v1`.
- قيود network/filesystem/capabilities/resources.
- Validator يستخدم Sandbox عند تفعيله.
- اختبار Windows الخاص بترتيب تنظيف `TempDir` تم إصلاحه.
- اختبارات `config` و`claudeorchestrator` و`sandboxrunner` و`daemon` و`integration` ناجحة.
- آخر commit منشور وقت إعداد هذه الوثيقة:
  - `815610e feat: run validator inside orchestrator sandbox`

### ما لا ينبغي اعتباره مكتملًا بعد

- اختبار Docker End-to-End حقيقي من بداية Run إلى نهايته.
- تشغيل مزود Claude وDeepSeek حقيقي داخل سياسة أسرار مكتملة.
- ربط API الداخلي بالـdaemon الإنتاجي مع جميع حواجز الشبكة.
- Persistence كامل للـRuns والاستئناف بعد إعادة التشغيل.
- Cost enforcement حقيقي أمام فواتير المزود.
- Sandbox لكل Adapters المراجعة الأخرى.
- حل كامل لـsymlink/TOCTOU عبر كل مسارات الملفات.
- تشغيل متوازٍ آمن مع جدولة واعتماديات.
- واجهة UI كاملة لعرض Orchestrator.

أي تقرير من نموذج آخر عن ثغرات أو مشاكل يجب تحويله إلى:

1. ادعاء محدد.
2. طريقة إعادة إنتاج.
3. تأثير واضح.
4. ملف أو سطر متأثر.
5. اختبار يفشل قبل الإصلاح.
6. إصلاح.
7. اختبار ينجح بعد الإصلاح.

لا نعتبر عبارة "مليار ثغرة" نتيجة تدقيق حتى توجد أدلة قابلة لإعادة الإنتاج.

## 9. تعريف النجاح للـMVP

نعتبر النسخة MVP ناجحة إذا استطاعت تنفيذ السيناريو التالي بشكل قابل للتكرار:

1. المستخدم يرسل هدفًا واحدًا.
2. Claude يولد خطة ذات مهام ومعايير قبول.
3. النظام ينشئ Worker واحدًا على الأقل في Worktree معزول.
4. العامل ينفذ أمرًا ثابتًا داخل Docker Sandbox.
5. العامل لا يصل إلى الشبكة أو خارج Worktree.
6. Validator ينفذ اختبارًا ثابتًا داخل Sandbox نفسه.
7. فشل الاختبار يجعل المهمة `failed` أو `held`، وليس `completed`.
8. المخرجات محدودة ومُنقّحة من الأسرار.
9. يمكن إلغاء التشغيل دون عمليات متروكة.
10. يظهر تقرير يربط Run وTask وAttempt وWorktree وSandbox.
11. لا يحدث Merge تلقائي دون موافقة المستخدم.
12. تعاد العملية نفسها بنتيجة متوقعة عند تشغيلها مرة أخرى.

---

## 10. تعريف النجاح للإصدار القابل للاستخدام

- لا توجد أسرار في Renderer أو Logs أو DB.
- لا يوجد تنفيذ Shell غير مقصود.
- لا يوجد Mount خارج النطاق المقصود.
- كل تشغيل له مهلة وحدود موارد.
- يمكن إيقافه واستئنافه بأمان.
- يمكن تفسير كل قرار.
- يستطيع المستخدم معرفة ما حدث دون قراءة Logs خام.
- يستطيع النظام تحمل فشل مزود أو Docker أو GitHub.
- كل Route له عقد واختبارات.
- كل تعديل API يمر عبر التوليد الرسمي.
- تعمل اختبارات Windows وLinux.
- توجد آلية تعطيل فوري للميزة.
- لا يتم توسيع النطاق قبل نجاح بوابة الأمان.

## الخلاصة

المنتج النهائي ليس مجرد "وكيل يستدعي وكلاء آخرين". المنتج هو **نظام تشغيل آمن للعمل البرمجي متعدد الوكلاء**:

- Claude يخطط ويقود.
- النماذج المتخصصة تنفذ.
- Worktrees تمنع تصادم الملفات.
- Docker يمنع التوسع غير المصرح للصلاحيات.
- Validator يطلب دليلًا قابلًا للتنفيذ.
- GitHub وCI والمراجعات تغلق حلقة الجودة.
- Kanban يجعل الحالة مفهومة للمستخدم.
- سجل التدقيق يجعل كل قرار قابلًا للمراجعة.
- المستخدم يحتفظ بالسيطرة على الأسرار والإنفاق والدمج.

الأولوية الآن ليست إضافة أكبر عدد من النماذج، بل إثبات دورة صغيرة كاملة وآمنة من **خطة → Worker → Sandbox → Validator → Review → قرار**، ثم توسيعها تدريجيًا.
